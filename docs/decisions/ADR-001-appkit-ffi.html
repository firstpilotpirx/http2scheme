ADR-001: AppKit FFI in two adapters

Unsafe code for the menu bar app

Status

Accepted 2026-11-12, change local-link-server (design D15).

Context

The owner asked for an installer like VoicePuncher's: a menu bar app in a disk image that starts at login. The menu bar status item lives in AppKit and the login item in ServiceManagement. Both are Objective-C frameworks. Rust reaches them through objc2 0.6.4 and objc2-app-kit, objc2-foundation, objc2-service-management 0.3.2. Some of their calls are unsafe. Until now every crate forbade unsafe code.

Decision

  • Unsafe code is allowed in exactly two files of the menubar component: status_menu_handler.rs and sm_app_service_login_item_gateway.rs.
  • Each file opens with #![expect(unsafe_code, reason = "ADR-001: …")].
  • A one-line // SAFETY: comment stands above every unsafe block; a file holds at most three (R-080, scripts/arch/no-todo.sh).
  • The workspace lint table sets unsafe_code = "deny"; linkserver and the app keep #![forbid(unsafe_code)] at their crate roots.
  • just unsafe-count checks those forbids and counts the unsafe uses per file of menubar against metrics/unsafe.tsv (R-144).

Alternatives

OptionWhy rejected
tray-icon + mudaMore dependencies and their own event loop for a six-item menu; the login item still needs ServiceManagement.
A Swift helper appA second language and toolchain to build, test and sign.
A LaunchAgent only, no menu bar appNot the standard Mac install the owner asked for: no drag to Applications, no visible state.

Consequences

  • Positive: the same crates and patterns as VoicePuncher; one process, one language; the unsafe code is in two small files a reviewer can read at once.
  • Negative: those two files rely on AppKit's own rules (main thread, object lifetimes), which the compiler cannot check; their integration tests run on the main thread to cover them.
  • A new unsafe file needs a new ADR or an update of this one, and a row in metrics/unsafe.tsv.
